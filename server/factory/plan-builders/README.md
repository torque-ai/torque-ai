# `server/factory/plan-builders/`

Pure builder functions that take a work item (and optionally a project + an architect's raw output) and produce the various string-shaped artifacts the factory loop hands to the architect, the work item, and the worker:

- **markdown plan prompts** for the architect
- **plan documents** synthesized from architect output (file-edits JSON or numbered-task summaries)
- **task body specificity** strings (scope, validation command, file list)
- **work-item detail strings** (validation, success criteria, scope phrasing)
- **rejection payloads** when a plan fails plan-quality scoring or the plan-quality gate

Every file here is **pure** — no DB access, no shared state, no event emission. Anything load-bearing comes in through arguments. The only side effects are reads under `fs`/`path` performed by upstream `shared/` helpers that the builders call.

This boundary is part of the loop-controller refactor arc (Phase 1a). The baseline + reflection checkpoint plan lives at [`docs/findings/2026-05-14-loop-controller-baseline.md`](../../../docs/findings/2026-05-14-loop-controller-baseline.md).

## File map

| File | Owns | Used by |
|---|---|---|
| `prompt.js` | `buildAutoGeneratedPlanPrompt`, `buildPriorRejectionFeedbackPrompt` | architect PLAN stage |
| `from-output.js` | `buildPlanFromFileEditsProposal`, `buildPlanFromNumberedTaskSummary` + their parsing helpers (`extractNumberedPlanSummaryTasks`, `cleanNumberedPlanSummaryText`, `titleFromNumberedPlanSummaryTask`, `summarizeNumberedPlanTaskScope`, `unwrapWholeMarkdownFence`, `convertFencedBlocksToIndented`, `isPromptEchoTail`, `trimPromptEchoTail`, `indentForPlan`, `normalizeProposalOperationType`) | PLAN-stage architect output recovery |
| `task-spec.js` | `buildTaskScopeDetail`, `buildTaskValidationDetail`, `buildImplementationTaskTitle` + `getTaskSpecificityFilePaths`, `formatPlanDescriptionFileList` | plan augmentation, scope/validation phrasing |
| `workitem-spec.js` | `buildWorkItemValidationDetail`, `buildWorkItemSuccessDetail`, `buildWorkItemScopeDetail` | derived strings used inside task-spec + prompt builders |
| `quality-reject.js` | `buildPlanDescriptionQualityRejectPayload`, `buildPlanQualityGateRejectPayload`, `buildTerminalEscalationRejectReason`, `PLAN_DESCRIPTION_QUALITY_THRESHOLD` | gate-failure path that persists rejection metadata to the work item |

## Dependency direction

```
loop-controller.js
       │
       ▼
plan-builders/*  ──────►  shared/*
       │
       └─► task-spec → workitem-spec (sibling import)
       └─► from-output → task-spec (sibling import)
```

`shared/` modules **never** import from `plan-builders/`. Sibling imports inside `plan-builders/` flow only in one direction (toward `workitem-spec.js` and `task-spec.js`) so the dependency graph stays acyclic.

## Collective guarantee

Given a `WorkItem` and (optionally) a `Project`:
- builders return either a string (the requested artifact) or `null` (no output applicable).
- builders never throw on bad input — empty/missing fields produce conservative defaults.
- builders never mutate their inputs. Outputs are fresh strings/objects.
- inputs and outputs are documented as JSDoc `@typedef`s in `types.js`.

## What does NOT live here

- **Plan-quality scoring** (`scoreAutoGeneratedTaskDescription` and its rule set). Stays in `loop-controller.js` for now; will move when plan-quality scoring is extracted as its own phase. Several builders that need a score reference (`buildTaskSpecificityAdditions`, `augmentAutoGeneratedTaskSpecificity`, `buildImplementationTaskFromAnalysis`) are still in loop-controller; they will join this directory after that extraction.
- **Plan file I/O** (`readWorkItemPlanText`, `cleanupRecoveredSideWrittenPlan`, etc.). These touch the filesystem with side effects; they belong elsewhere — likely a future `plan-file/` cluster.
- **DB-bound work-item operations** (route, reject, advance). Those live in the lifecycle layer, not here.
